# Electron + Whisper Medium 实现计划

本计划是 [桌面版方案](./electron-whisper-medium-plan.md) 的执行清单。目标交付物是一个 Windows x64 安装程序：安装后无需 Python、Node.js 或 Ollama；用户可在应用内下载 Whisper Base、Small 或 Medium，并在 CPU 上转写；即时摘要、AI 建议和问答仅使用用户填写的兼容 Chat Completions API。

## 开工前约束

- 当前 `main` 工作区有未提交改动。实施时保留这些改动，先记录基线，不重置或覆盖用户数据及无关文件。
- Whisper Medium 作为默认与性能基线；同时提供 Base、Small 作为用户可选的轻量档位，所有模型均使用 CPU int8 并可按需独立下载。
- 现有 `start.ps1` 浏览器开发入口在迁移期间保留。桌面版与浏览器版使用同一业务后端，避免同时改动转写、摘要和 UI 协议。

## 当前进度（2026-09-23）

- 阶段 0：单路系统声音 10 分钟速度门槛通过；双路、全程内存和人工准确率验收未完成，见 [P0 记录](./whisper-medium-p0-results.md)。
- 阶段 1：已移除 FunASR 与 Ollama 路由，Whisper Base/Small/Medium 的 CPU 转写、本地 API-only 设置迁移与 token 上限已实现；干净 CPU 环境无 FunASR、PyTorch 或 CUDA。
- 阶段 2：已加入动态端口、启动就绪消息、桌面随机 Cookie 校验、模型按需下载接口及后端收尾退出接口；冻结版后端启动、鉴权、缺失模型保护与关闭冒烟测试通过。
- 阶段 3：已新增 Electron 主进程与安全窗口配置，并将已解压 Electron 运行时打入应用；实际安装后的窗口交互仍待手动验收。
- 阶段 4：已产出不含模型权重的 Windows x64 NSIS 安装包，约 219 MiB；尚未在干净 Windows 环境离线安装验收，也未实际下载完整 Whisper 模型。
- 增补：模型选择支持 Base（约 148 MB）、Small（约 486 MB）与 Medium（约 1.53 GB）；各自固定仓库修订版本、独立下载状态与安装目录。

## 阶段 0：基线与 Medium 性能验证

1. 固定 `Systran/faster-whisper-medium` 的具体修订版本，记录模型文件、哈希和许可。创建可重复运行的 10 分钟音频基准：分别覆盖中文连续发言、停顿、静音、系统声音和麦克风+系统声音。
2. 使用现有 faster-whisper CPU `int8` 路径，在参考 Windows 机器记录 CPU、内存、每段解码时间、录音到显示延迟、队列峰值及无声误识别。混合采集必须单独测，因为两个来源会竞争同一个解码器。
3. 运行现有后端测试和前端构建，记录基线结果与当前安装体积。

完成标准：得到可复现的性能报告。至少连续 10 分钟无音频丢失、队列不持续增长，识别总耗时不超过音频时长；记录 p50/p95 显示延迟与峰值内存。若不达标，先在阶段 1 调整分块、线程、解码参数再复测。此门槛决定能否把该版本称为“实时”。

## 阶段 1：业务代码收敛为 Whisper + API

4. 修改 `meeting_assistant/asr.py`：移除 FunASR、VAD、CT-Punc 与旧模型切换分支，使用 Whisper Base/Small/Medium 的 CPU `int8` 加载和现有幻觉过滤。每档固定模型修订版本，应用内独立下载到用户数据目录并显示进度；完成后离线转写。检查长句、停顿分段和结束会议时的尾音处理。
5. 修改 `meeting_assistant/audio.py`、`session.py`、`config.py`：删除 FunASR 专用的 200ms 帧和临时转写状态；默认模型为 Medium，用户可在设置中选择已下载的任一档位。保留原始 WAV、队列积压提示、会议结束时等待识别完成的行为。旧版设置迁移需幂等：有效的 Base/Small/Medium 选择保留，不支持的旧值回退到 Medium；旧 API 地址、模型名、密钥继续保留。
6. 修改 `meeting_assistant/summary.py` 和设置接口：只保留 `/chat/completions` 协议，删除 Ollama 路由和配置项。未填写 API 地址/模型/密钥时，转写正常运行，摘要状态显示“需要配置”；连接失败不覆盖已有摘要。旧 Ollama 设置迁移为“API 未配置”，不能把本机 Ollama 地址当作远程 Chat Completions 地址。
7. 修改 `frontend/src/SettingsDialog.tsx`、`App.tsx`、`types.ts`、`api.ts`：转写区域允许选 Base/Small/Medium，展示所选模型的下载状态和进度；摘要区域只保留 API 地址、模型名、密钥和连接测试；删除 FunASR/Ollama 说明。保留原有会议页面布局与历史记录。
8. 从 `pyproject.toml`、`requirements-lock.txt` 和安装脚本移除 FunASR、ModelScope、PyTorch、kaldi-native-fbank 及不再需要的传递依赖；在**新建的干净虚拟环境**验证安装，避免旧 `.venv` 残留掩盖依赖问题。更新 `scripts/smoke_asr.py`、README 和相关测试。

完成标准：后端测试、前端构建、真实音频冒烟测试通过；干净虚拟环境中没有 GPU/FunASR/PyTorch 包。无 API 配置时可完成录音、转写、历史记录和导出；有 API 配置时摘要与问答正常。

## 阶段 2：桌面后端启动协议与数据路径

9. 修改 `meeting_assistant/config.py`、`app.py`、`launch.py`：将资源根目录、模型目录、前端构建目录、数据目录分别配置。开发入口仍可使用固定 `8766`；Electron 模式只监听 `127.0.0.1` 随机端口，准备好后向父进程输出一条机器可解析的就绪消息。不要把普通日志混入就绪消息。
10. 为 Electron 模式增加每次启动随机凭据。主进程先设置本机 HttpOnly Cookie，再打开页面；后端对所有 `/api` 请求（含 SSE、导出）验证凭据。现有 Host/Origin 校验改为当前监听端口，并保持浏览器开发入口可用。确认无凭据的本机浏览器页面不能调用录音接口。
11. 增加受控退出流程：桌面主进程调用停止会议，等待尾音、最终摘要和数据库落盘，再请求后端正常退出。异常退出时沿用现有中断会议恢复。数据、模型和日志分别放到 `%LOCALAPPDATA%\MeetingAssistant\data`、`models` 和 `logs`。旧 `data/` 只做明确的一次性导入和备份，不删除原目录。

完成标准：桌面后端可由测试脚本独立启动、读出动态端口、验证凭据、完成一次会议并正常退出；重启后历史记录和密钥仍在，旧数据导入可重复执行而不产生重复会议。

## 阶段 3：Electron 开发版

12. 新增 `desktop/`：Electron 主进程负责单实例锁、启动后端子进程、等待就绪、加载同源页面、错误页、日志、窗口导航限制和退出收尾。窗口使用 `nodeIntegration: false`、`contextIsolation: true`、`sandbox: true`；前端不直接接触文件系统或模型。
13. 开发时调用 `.venv` 后端；打包时调用资源目录中的后端 exe。两条路径共用同一个启动协议。若后端启动失败、服务崩溃或超时，窗口显示可理解的错误与日志位置，而不是空白页面。模型缺失时主页面引导用户下载。

完成标准：`desktop` 开发命令启动后，窗口内能完整执行开始录音、实时转写、停止、摘要、历史记录和导出；再次启动聚焦已有窗口，不产生第二个录音服务。

## 阶段 4：可复现打包与安装程序

14. 用 PyInstaller `onedir` 打包 Python 后端，检查 `sounddevice`、`soundcard`、`av`、CTranslate2 等原生库以及前端静态文件在冻结环境中的路径。先验证独立后端 exe，再放入 Electron 资源目录；模型不进入安装包，首次使用时下载到用户数据目录。
15. 构建便携版，验证首次在线下载、下载中断后重试、下载完成后的离线加载、程序目录只读时的数据写入、升级后路径稳定性；记录压缩包、安装后目录、峰值内存和冷启动时间。
16. 产出 Windows 单一安装程序。安装器放置 Electron、后端和前端，不依赖系统 Python/Node；Whisper 权重由用户在应用内选择并下载。准备图标、版本信息、许可文件、卸载行为和发布前签名流程。卸载默认保留用户会议数据，清理时须明确告知。

完成标准：在干净 Windows 10/11 x64 虚拟机中，无 Python、Node、Ollama 和预先缓存模型时安装；分别选择并下载 Base、Small、Medium 后完成本地录音和转写，断网后再次转写仍可用；配置有效 API 后完成摘要和问答。

## 阶段 5：发布验收与交付

17. 自动化：保留 Python 单元/接口测试与 React 构建检查；补充桌面启动协议、权限校验、设置迁移、退出收尾和打包后冒烟测试。对硬件相关的麦克风与 WASAPI loopback 做人工验收。
18. 人工矩阵：无 API、有效 API、API 断网/超时；静音与连续讲话；麦克风、系统声音和混合采集；录音中关闭窗口；后端崩溃；端口占用；重复启动；升级安装；旧数据导入。
19. 更新 README 为桌面安装与首次配置说明，提供安装包、构建步骤、模型/依赖版本与哈希、性能报告和已知限制。发布报告应写明测试 CPU/内存和实际延迟，不能笼统保证所有 CPU 都实时。

## 依赖关系与停点

执行顺序为 `阶段 0 → 阶段 1 → 阶段 2 → 阶段 3 → 阶段 4 → 阶段 5`。阶段 0 的性能结果是发布门槛，但不阻止开发桌面壳；阶段 1 的单路径设置迁移必须先于正式打包。每个阶段结束都运行对应测试并保留可启动版本，避免把功能精简、进程管理和打包故障混在一起排查。

如果所选模型在参考 CPU 上持续慢于实时，应提交具体测量值和优化尝试；界面明确说明模型大小与准确度、速度的取舍，不对所有 CPU 硬件作实时承诺。
